# FC-like 游戏指南

本指南适用于项目明确标记为 FC-like 的游戏。它建立在[普通游戏开发指南](./game-guide.md)之上，只补充 FC/NES 复刻常见的运行框架、显示和输入约束，不统一规定某类游戏的规则、物理模型、碰撞顺序或关卡设计。

## 项目声明

开始开发前应明确：

- 参考的原作和版本。
- 目标逻辑分辨率和宽高比。
- 目标逻辑频率。
- 地图或基础单位尺寸。
- 目标设备、屏幕方向和输入方式。
- 复刻重点是规则、体验还是尽量精确的帧行为。
- 允许加入的现代化调整。
- 当前已知的原作差异。

这些内容记录项目自己的决策，不进入公共指南。

## 代码结构

FC-like 游戏沿用普通游戏的 App 和 Dialog 结构：

```text
XxxGame.vue
└── XxxApp
    └── DialogMgr
        ├── StartDialog
        ├── PlayDialog
        │   ├── PlayInputMgr
        │   ├── PlayGameView
        │   ├── PlayHudView
        │   └── 游戏自身需要的功能模块
        └── ResultDialog
```

- 当前关卡能力由 `PlayDialog` 持有，跨关卡数据放在 `app.data`。
- 输入、地图、相机、实体或其他能力只有在内容复杂时才拆成 `Play` 前缀文件。
- 不要求所有 FC-like 游戏具有相同模块，也不建立统一规则链。
- 不把某个现有复刻项目的类名和实现细节反向写成公共标准。
- 关卡较多时可以建立 `level/` 保存数据和编辑器源文件；实体资源仍放在 `assets/`。

示例目录：

```text
src/xxx/
  普通游戏基础文件
  PlayDialog.js
  PlayInputMgr.js
  PlayGameView.js
  PlayHudView.js
  PlayMap.js             可选
  PlayCamera.js          可选
  PlayDebug.vue          可选
  level/                 可选
  assets/
```

## 固定逻辑画面

- 游戏使用项目声明的固定逻辑分辨率，浏览器视口只改变显示布局和缩放。
- 视口尺寸、设备像素比和屏幕旋转不得改变速度、地图单位或其他玩法参数。
- 默认保持原作或项目声明的宽高比，不分别拉伸横轴和纵轴。
- 游戏世界、HUD、触控控制器和浏览器外壳分别布局。
- HUD 固定在屏幕或逻辑画面坐标，不跟随世界相机震动和缩放。
- 超宽屏默认通过留边、外壳或背景承接，不因空间变宽自动扩大原作视野。
- 如果项目决定扩大视野、改变 HUD 位置或裁切画面，应在项目声明中记录。

## 像素渲染

- 像素素材默认关闭纹理平滑。
- 空间允许时优先整数倍显示；空间不足时可以整体非整数缩放，但不得改变逻辑坐标。
- Sprite、图块和相机是否强制整数逻辑像素对齐，由项目的复刻精度决定。
- 像素素材避免无必要的任意角度旋转和局部非整数缩放。
- 逐帧动画频率可以低于逻辑更新频率，显示帧不能成为玩法状态的唯一来源。
- 外层掌机、背景和现代 UI 可以使用更高分辨率，但不能使核心游戏画面模糊或变形。

## 时间与更新

- 玩法参数使用逻辑单位和秒，不使用每个渲染帧固定增加数值的写法。
- `delta` 必须限制上限，避免切回页面后一次推进大量时间。
- 追求稳定或接近原作帧行为时，应该使用固定逻辑步；简单且不依赖精确帧行为的游戏可以使用限制后的可变时间步。
- 使用固定逻辑步时，应限制单个渲染帧的最大补算次数，并在暂停、切后台和恢复时清空累计时间。
- 渲染插值只能改变表现，不能改变玩法结果。
- 需要复现随机行为时，规则随机数应支持固定种子；表现用随机数与玩法随机数分离。

本指南不规定统一的逻辑更新顺序。每个游戏根据原作行为组织自身更新，只需保证同一输入和初始状态下的结果稳定、可解释和可测试。

## 地图与关卡数据

存在地图或固定关卡数据时：

- 关卡优先由数据生成，不把关卡结构硬编码在显示对象创建流程中。
- 图片负责显示；阻挡、危险、可破坏和可交互等信息由关卡或对象数据表达。
- 地形、对象、装饰和触发器应在数据概念上可区分，装饰不应意外参与玩法判断。
- 地图数据保存类型、位置和必要参数，不保存需要动态执行的脚本字符串。
- 需要检查点、调试或状态恢复的对象应具有稳定实例 ID。
- 相机范围、出口和离屏边界由关卡数据或明确常量定义，不从背景图片推断。

没有地图的固定屏游戏不需要为了符合结构而创建地图模块。

## 输入与虚拟控制器

- `PlayInputMgr` 输出方向、动作等语义状态，不直接修改角色坐标或其他玩法数据。
- 键盘、手柄和触控使用来源集合合并；任一来源仍按下时，对应动作保持按下。
- 区分按下沿、持续按住和松开沿，具体动作使用哪种语义由游戏决定。
- 页面失焦、指针取消、失去捕获、Dialog 停用、暂停和销毁时释放输入。
- 触控控制器必须支持多指，方向和动作键不能互相抢占指针。
- 横屏可以默认左侧方向、右侧动作，但具体布局由游戏画面和原作操作决定。
- 动态摇杆应具有本次落点原点、死区、最大偏移和松手回中。
- 固定方向键、动态摇杆和滑动区域均可使用，不强制所有 FC-like 游戏采用同一种控制器。
- 触控控件避让安全区、HUD、玩家附近和关键落点。
- 手柄轴值应有死区，手柄断开时释放对应来源。

## 画面层级与动效

建议按以下层级组织：

```text
游戏背景和世界
HUD 与常驻控件
命中、爆炸、拾取等短时表现
暂停、设置和结算界面
浏览器外壳与调试工具
```

- 玩法状态与显示帧分离，换动画帧不应意外改变判定。
- FC-like 可以使用逐帧、闪烁、调色和短位移表达反馈，不要求套用现代弹性 Tween。
- 现代外壳和 DOM UI 仍遵循[游戏动效、缓动与 UI 设计指南](./motion-ui-guide.md)。
- 减弱动效应减少镜头和大范围运动，但保留理解玩法所需的命中、受伤和状态反馈。

## 音频

- 原作风格音效仍通过游戏自己的资源清单和 `AudioMgr` 管理。
- 高频发射、移动、命中等音效限制并发数量。
- 循环移动和环境音效随对应状态开始和停止。
- 暂停、切后台、Dialog 销毁和游戏退出时停止持续音频。
- 原作音效和现代外壳 UI 音效可以按项目需要分组控制。

## 调试与复刻验证

复杂 FC-like 游戏可以按需提供：

- 选关和重开。
- 暂停和单步推进。
- 调整逻辑速度。
- 显示逻辑坐标、网格或判定区域。
- 查看当前输入和关键状态。
- 固定随机种子。
- 设置生命、能力、敌人或道具。
- 对比原作关键帧和已知差异。

调试能力不能改变正式模式的默认行为，调试 UI 和事件也必须随所属组件销毁。

## 完成检查

- 项目明确记录目标分辨率、逻辑频率、输入方式、复刻重点和允许差异。
- Canvas 缩放、设备像素比和屏幕旋转不会改变逻辑世界。
- 游戏画面保持目标宽高比，没有非预期拉伸或关键内容裁切。
- 像素素材的平滑、整数对齐和缩放策略与项目声明一致。
- 不同刷新率下游戏速度和关键行为基本一致。
- 暂停、切后台和恢复后不会一次推进大量时间。
- 地图由数据驱动时，显示素材不是玩法属性的唯一来源。
- 键盘、触控和手柄不会错误释放其他来源仍保持的动作。
- 页面失焦、Dialog 覆盖、暂停和销毁后没有卡键。
- 动态摇杆或方向控件满足项目声明的死区、回中和多指要求。
- 重开和切关后没有遗留显示对象、Ticker、事件或持续音频。
- 桌面和目标移动端没有滚动、控件重叠或文字溢出。
- 已知的原作差异已经记录，而不是隐含在实现中。
